监管递交与可复现性

第 0 章教你用 renv 锁住项目，第 4 章教你留追溯清单，第 5 章教你做包验证。本章把这三件事放到同一个问题下重新问一遍：审评员拿到你的递交包，在另一台机器、另一个操作系统上，能不能把结果重跑出来？

本章是主线九章之后的进阶专题，不重排原有编号。配套可运行案例见 C7 最小可复现递交包；本章所有标注「实跑捕获」的输出都来自 R 4.5.0 真实运行。

9.1 监管口径：谁验证、验证什么

先把最容易误读的一句话钉死：FDA 不"验证"也不"批准"任何编程语言。FDA Statistical Software Clarifying Statement 的立场是软件须 reliable，不指定 SAS 或 R；R Consortium 的 Pilot 是可行性证据——公开递交包被审评员接收并复现，而不是「R 拿到了认证」。Pilot 3 的反馈里写得很直白：选择足够可靠的开源包，责任在申办方。

所以验证对象从来不是语言，而是这三层（与第 5 章 5.8 的 GAMP5 表对齐）：

层验证对象R 世界的证据
流程脚本、推导逻辑、双编程与 QCtestthat 断言、diffdf 比对、spec 双向链接、评审记录
环境钉死且可重建的计算环境renv.lock、sessionInfo()、R/Rtools 版本、必要时容器镜像
控制变更、权限、审计追踪、数据完整性Git commit、CI 日志、logrx 执行日志、ALCOA+、Part 11 电子记录控制

对临床统计编程真正对口的是下面这一组，别被会议论文里的"法规趋同"带偏：

文件对临床统计编程的作用
ICH E6(R2)/(R3) GCP §5.5电子数据处理系统的验证、SOP、审计追踪与数据完整性（最直接的上位要求）
21 CFR Part 11电子记录与电子签名：系统验证、访问控制、审计追踪、记录保全
ICH E9 / E9(R1)统计原则与 estimand，决定「什么算需要复现的结果」
FDA Study Data Technical Conformance Guide v5.7§4.1.2.10 要求递交源码为单字节 ASCII 文本，并在 ADRG 写明软件版本与操作系统；§2.3 说明 ADRG 的定位
eCTD 规范 / Data Standards Catalog文件格式、模块与传输；见 9.2 的版本号
GAMP 5 2nd ed（ISPE 行业指南，非法规）风险分类与生命周期框架，可平移到临床系统；不是法条
ICH M11 / CDISC / Define-XML / Pinnacle 21数据标准与 conformity 校验，见第 2、4 章
趋势提示（非正式适用依据）：PharmaSUG 2026 ET-292 把 FDA CSA、EU GMP Annex 11 修订草案与 Annex 22（AI）并列为"监管趋同"信号，主张风险化、证据驱动的软件保证。但三者都不是临床统计编程的对口 guidance：FDA CSA 最终版（2026-02，取代 2025-09）正式范围是医疗器械生产与质量管理体系软件，且不改变 Part 11 义务；Annex 11 现行 2011 版适用于药品 GMP 计算机化系统，2025-07 修订草案尚无最终版与生效日；Annex 22 是 GMP 下 AI 治理的草案。此处仅记录行业理念迁移，不得作为临床统计编程的合规依据引用；实际项目以公司 QA/RA 与当期法规为准。
SAS 误区：把「R 已被 FDA 接受」当成「我这套脚本自动合规」。SAS 也不是被 FDA 逐项目验证的；SAS 的优势是公司统一环境 + PROC 版本随 SAS 版本整体锁定。R 的包版本是分散的，所以你必须自己造出等价的证据链——这正是本章剩下的部分。

测验 1：关于「R 能否用于 FDA 递交」，下列哪句最准确？

选 B。Statisticial Software Clarifying Statement 只要求软件 reliable、不指定语言；Pilot 1–5 的公开递交包被审评员接收并复现，是可行性证据而非认证。R Consortium 在 Pilot 3 反馈里明确：由申办方负责选择足够可靠的开源包。

9.2 七个 Pilot 与 2026 时间线

第 0 章 0.1 写的是「Pilot 1–5」，那是 2025 年的口径。截至 2026 年，R Consortium Submissions WG 已有七个 Pilot。把时间线读一遍，你会发现每个 Pilot 都在回答同一个问题的不同侧面：审评员怎么把结果跑出来。

9.3 七层环境复现证据链

把第 4 章 4.8 的追溯清单抬到递交级，会得到下面这条链。任何一层缺证，审评员的重跑就可能停在那一步。

层锁什么工具 / 产物常见失效点
L1 代码精确的程序版本Git commit SHA、.txt 源码只写"最新版"
L2 包每个包及其来源、版本renv.lock、package_versions.tsv、pkglite / .zip 闭源包把 sponsor 端 lockfile 直接搬给审评员
L3 运行时R 版本、Rtools、OS、BLASsessionInfo()、ADRG §7Rtools 与 R 版本不匹配
L4 运行环境系统库与依赖整体Docker / Podman 镜像、webR审评端装不上容器（见 9.6）
L5 数据输入与产物的字节级身份md5、只读输入快照、XPT v5 / Dataset-JSON中间 rds 文件未清理、输入可写
L6 执行谁在何时跑了什么logrx / logger 日志、stdout+stderr只有控制台输出，没落盘
L7 文档把上面六层讲清楚ADRG、programTOC、Define-XMLADRG 只写"用 R 完成"
# 在审评端重建环境（不是搬运申办方的 lockfile）
source("programs/00_install_packages.R")   # 从 CRAN / 内部仓库装指定版本
renv::init(bare = TRUE)
renv::snapshot()                            # 在审评员本机生成 renv.lock
writeLines(capture.output(sessionInfo()), "logs/session.txt")
逐行解读：
  1. 先按 ADRG 的包清单装指定版本。Linux 上生成的 renv.lock 不能原样搬到 Windows：J&J 的做法是给安装脚本，让审评员在本机 snapshot 出自己的锁文件。
  2. init(bare=TRUE) 建干净私库，snapshot() 冻结实际装到的版本——这一步的产物本身就是「环境已复现」的证据。
  3. sessionInfo() 补上 lockfile 不含的部分：R 版本、平台、locale、已加载包。
为什么 R 版本要事先沟通：Pilot 3 的教训之一是跨环境 R 版本不一致；Pilot 5 把 R 固定为 4.4.3，并在 ADRG 里补上「Rtools 版本须与所用 R 版本对应」的说明。递交前的 pre-submission correspondence 就该把这套运行时说清楚。

测验 2：申办方在 Linux 上开发，审评员用 Windows，最稳妥的做法是？

选 C。lockfile 记录的是特定 OS/库路径下的解析结果，跨 OS 不可搬运；J&J 的 ADRG 附录与 R/Pharma 2026「recipe」讨论都指向同一结论——递交的是能重建环境的配方，不是一份冻结的二进制状态。

9.4 ADRG：从「附录」到「标准文档」

ADRG（Analysis Data Reviewer's Guide）是审评员读分析数据集与程序的第一入口。PHUSE 的 ADRG Package WG 提供填写指南；其 OSDocuMeta / Version Metadata for Open-Source Languages 项目专门解决一个新问题：SAS 时代 ADRG 里写「SAS 9.4」就够了，R 时代必须逐个包声明版本。该项目已起草 ADRG R 填写指南、示例与 {adrgOS} 包（Quarto 模板 + 章节填充函数，仍在评审中，依赖 PHUSE ADRG 标准组）。

pharmaverse eSubmission 建议 ADRG 至少写明五项：

  1. 使用的 R 版本；
  2. 主要开源 R 包的描述、各自版本、获取来源（尤其非 CRAN 来源）；
  3. 所用闭源包的描述；
  4. R 与指定包版本的安装说明（要覆盖 Windows）；
  5. 程序与目录结构说明，可另用 programTOC 文档。

闭源包两条路：pkglite::pack() 打成纯文本束（Pilot 1），或压缩 .zip（Pilot 3 起，v9.3 后更顺）。下面是可直接抄进 ADRG 的中文骨架：

【第 7 节 · 程序递交】
本次递交的全部分析数据集与主要/次要疗效结果程序均以 R 编写，开发平台为 Linux，
R 版本 4.4.3；源码以单字节 ASCII 文本（.txt）提供。所用包、版本与来源见附表
package_versions.tsv；非 CRAN 来源与内部包单独列示。闭源包 c7pkg 以
r0pkg.txt（pkglite 文本束）提供，亦可按 eCTD 文件格式规范 v9.3 以 .zip 提供。

【第 9.1 节 · 附录 1：重建 R 分析环境】
1) 安装与第 7 节一致的 R 版本，并安装与之匹配的 Rtools；
2) 运行 00_install_packages.R，从 CRAN / 申办方内部仓库装回附表中的精确版本；
3) 请勿直接复制申办方在 Linux 上生成的 renv.lock（跨操作系统不通用）；
   请在本机执行 renv::init(bare = TRUE) 与 renv::snapshot() 生成 LOCAL 锁文件；
4) 按 programs/ 下顺序运行各 .txt 程序，输出与 datasets/adsl.xpt 比对；
5) 将 sessionInfo() 与 logs/ 下的执行日志一并归档，作为复现证据。
【版本差异】预先声明与 SAS 结果允许的数值容差及舍入规则（见 9.6）。

C7 脚本会真的生成一份英文 ASCII 版 ADRG 骨架（教学用，非递交就绪文档）：

SAS 误区：以为 ADRG 是"程序清单 + 一句 SAS 版本"。R 的 ADRG 还承担环境重建说明书的角色：包版本、来源、OS 差异、装包顺序、Rtools 版本、如何判断重跑成功，都要写到审评员照着做就能跑通的程度。

9.5 包风险与验证：R Validation Hub 体系

第 5 章 5.8 讲了 valtools 与 riskmetric / risk.assessr，但没交代这套东西的出处。R Validation Hub（pharmaR） 是跨公司协作，其白皮书 A Risk-based Approach for Assessing R Package Accuracy within a Validated Infrastructure 给出的核心主张是：不做"语言认证"，按风险分级评估每个包是否 fit for intended use。

library(riskmetric)
# 一次标准评估：引用 -> 评估 -> 打分 -> 汇总
ref <- pkg_ref("dplyr", source = "pkg_cran_remote")
a   <- pkg_assess(ref)
s   <- pkg_score(a)
print(head(as.data.frame(s), 8))
# 离线安装源可改用 pkg_ref("dplyr")（class: pkg_install）

这排 NA 就是本章最该记住的细节：封闭验证环境里，覆盖率、远程 check、下载量、reverse deps 这类需要联网或额外工具的指标无法求值，应如实记为 NA，而不是补 0 或凑分。评估族覆盖维护（maintainer/news）、文档（vignette/help）、测试（coverage/R CMD check）、社区使用（downloads/reverse deps）与规模依赖（codebase/dependencies）；但 accuracy（代码算得对不对）不在打分范围内，须由组织自行判断。

边界：riskmetric 给的是证据，不是判决——验收阈值与最终放行必须由人签。封闭验证环境里，下载量、reverse deps、远程 check 等联网指标会返回 NA，如实记录即可，不要凑分。另注：valtools 对 R 4.5.0 当前无 CRAN 版本，需从 PHUSE/pharmaverse 的 GitHub 安装。

9.6 容器 / WebAssembly / 跨平台边界

「打个 Docker 镜像就能复现」是最诱人也最容易在递交场景翻车的想法。Pilot 4 的 FDA 回函（2026-05） 给了很实际的答案：

方案FDA 回函 / 行业反馈对笔记前八章的影响
WebAssembly / webR浏览器即用，审评员更偏好；但仍需 renv 还原构建依赖，还要起一个 web server 进程renv 没被替代，反而仍是地基
Docker / Podman 容器整体打包 OS + R + 系统库，可移植性最好；但 Docker Desktop 需 WSL、FDA 笔记本安装受限（许可）、构建性能不稳，尚未消除手工配置容器是 L4 的候选，不是 L2/L7 的替代品
纯 renv.lock + ADRG已由 Pilot 1/3/5 与 J&J 实际走通仍是 2026 年最可依赖的默认路径

R/Pharma 2026「Reproducible Environments」圆桌 把问题概括成一份要能扛过 OS 更换的 recipe：申办方多在 Linux（常容器化），审评方多在 Windows；组织既需要锁定环境（拿镜像即可重跑）也需要开放环境（日常开发）；与其每个项目从 base R 叠 renv/rv/uv，不如约定一个跨项目共同核心包基线，只叠加项目特有部分。同场 EU Summit 圆桌（2026-10-05） 对「开源递交的顾虑解决了吗」给出的短答案是 Not Fully：审评员不熟 R、缺技术支持、包栈随时间演进、复现失败时没有支持模型，都仍是开放问题；讨论中的建议包括更清晰的 ADRG 模板、视频演示、由统计师作第一联系人、预先声明可接受差异，以及业界共建审评方友好的可安装环境。

数值可复现性是另一条独立的线。即使环境完全一致，BLAS、编译器、舍入规则也会让 R 与 SAS 结果有微小差异：PHUSE CAMIS 项目专门比对 R / SAS / East 在同一方法下的结果差异；Atorus 2026 为对齐 SAS 舍入专门写了函数并全表统一应用。经验做法是在 ADRG 中预先声明容差与舍入规则，并把「双编程 + diffdf 比对」的边界从"数据相同"扩展到"数值在容差内一致"。

9.7 开源治理与 DevSecOps

PharmaSUG 2026 ET-292 把第 5 章的 CI 章节再往外推一层：当 R 从散脚本长成跨研究复用的包与流水线，风险不再只是"代码写错"，还包括凭据泄露、机器间结果漂移、依赖变更引入漏洞、非交互环境跑挂、日志/产物泄漏敏感数据。它给出的三层架构可直接贴到第 5 章 5.7 的 GitHub Actions YAML 旁边：

9.8 递交级自检清单（可直接贴进项目 README）

  1. 代码版本：Git commit SHA 已记录，程序以 ASCII .txt 提供（SDTCG §4.1.2.10）。
  2. 包清单：ADRG 附表列出每个包的版本与来源，非 CRAN / 内部包单独标注。
  3. 环境配方：ADRG §9.1 给出安装脚本、R 版本、Rtools 匹配说明与「在本机重建 lockfile」的指示。
  4. 运行时留痕：sessionInfo() 与包版本表已归档。
  5. 输入只读：输入快照 md5 已记录，中间产物（rds 等）不进入分析输入链。
  6. 数据格式：XPT v5 已生成并过 Pinnacle 21；若用 Dataset-JSON，注明 v1.1 校验工具的当前支持状态并保留 XPT 双轨。
  7. 闭源包：pkglite 文本束或 .zip 其一已提供，文件名符合 eCTD 约定。
  8. 执行日志：logrx / logger 落盘，stdout+stderr 全收，含时间与运行人。
  9. 验证证据：包风险评估（riskmetric / risk.assessr）、testthat 回归、CI 日志、valtools 追溯矩阵齐备。
  10. QC 与容差：双编程 diffdf 结果归档；ADRG 预声明与 SAS/其他语言的舍入规则与可接受数值差异；产物清单（file + md5 + bytes）已生成。
